# Process review: how the work is done, and what causes the bugs

**Date:** 2026-10-15 · **By:** the orchestrating session (Claude Opus 5.5), at the owner's request · **At:** master `30c2c80`

The question: how is the process working, what causes most of the bugs, whether there are too many tests, too few or the wrong ones, and whether there is enough code review.

The figures before 2026-10-09 come from [the bug-attribution audit](2026-10-09-bug-attribution.md), which an agent wrote. The later bugs come from the commits merged between 2026-10-10 and 2026-10-14.

## Short answer

- **Most bugs live in the seams between systems, not inside them.** Each system passes its own tests. The faults appear where jobs, items, buildings, health and animals meet, and several whole features turned out never to have worked end to end.
- **The test count is about right; the shape is wrong.** There are about 71,000 lines of tests for about 71,000 lines of code, and 2,683 tests. Many tests set up the very state the code under test is supposed to produce. And for a while, long chaotic runs were used as pass/fail gates, which blocked correct fixes.
- **There is almost no code review.** The orchestrator reviews commit messages, test results and file lists, not the diffs. When one agent did read another's code, it found bugs.
- **A large share of everyone's effort went to process, not the game:** quota juggling, cut-offs and resumes, backlog merge conflicts, and paperwork.

## 1. What causes the bugs

The bug-attribution audit counted 124 bugs. They were found by audits and long runs, almost never by the test suite:

| Found by | Bugs |
|---|---|
| T-115 bug hunt (incl. spec reading) | 48 |
| UI audit of v1.0.0 | 30 |
| M5 audit | 12 |
| Balance and mood measurements, long runs | about 20 |
| Triage, reviews and other work | about 14 |

By kind, they were:
- **wrong logic:** 36;
- **UI:** 26;
- **faults in the spec itself:** 22;
- **missing validation:** 16;
- **missing cleanup:** 14.

Since then the pattern has been the same, and starker: whole features that never worked from end to end.

| Fault | Why no test caught it |
|---|---|
| Wild animals never spawned until T-192 | Fixtures did not use them |
| The hospital chest was never stocked (T-301): a built chest is not walkable, so the haul job was blocked forever | `hospital_run` places cloth and thread straight on the hospital tile |
| Several grazers fed by one grass tile (T-285) | The pasture test only passed *because* of this bug |
| Pasture capacity off by 8× (T-210) | A spec number nobody had measured |
| Orphan reservations (T-263), reserved barrels hauled away (T-132), immigrants arriving in an unconnected area (T-260) | Only long runs reach these states |

**The common cause is staging.** Scenario files call `spawnItem` 156 times, and 33 test files turn wild animals off. Each test checks one system given perfect inputs. Nothing checks that the game, played from player commands alone, actually delivers those inputs.

The spec is also a real source of bugs: 22 of the 124 were spec faults, and some of its numbers had never been measured.

## 2. Tests

**Not too many and not too few: they are the wrong mix, and they are slow.**

- **Missing: player-path tests.** These are tests that start from commands only: build the chest, set the labors, place the order, and check the outcome. Every "never worked" bug above is of that kind.
- **Wrong: chaotic runs used as gates.** The browser year as a floor that could only go up, then the second-worst seed of twelve, each blocked correct fixes: T-137, T-261, then T-211 and T-301, costing several days. T-308 fixed this by guarding the sum of the living. The general lesson is to measure a figure's noise before making it a gate.
- **Weak: render goldens.** Two fifths of the UI tasks since 2026-10-11 moved at least one golden. They are regenerated by the same agent that changed the screen, so they show that something changed, not that it is right.
- **Self-certified expectation changes.** "This test asserted exactly the old behaviour, so I updated it" appears in 11 recent commits. It is usually honest, but nobody checks it.
- **Slow.** `npm test` takes 8–14 minutes, e2e 4–7, and the instrument 10–25. A behaviour task needs 30–45 minutes of gates, then the orchestrator re-runs the static checks and `npm test` on master. Agents were often cut off mid-gate.
- **What works:** failing test first, the twelve-seed instrument with the sum rule, and the invariant checks. The invariants are what exposed T-302 to T-304 in the sweep.

## 3. Code review

Today the only reviews are:
- commit messages;
- the "e2e: N passed" line;
- the orchestrator's static checks and `npm test` on master before each push.

Three weaknesses follow from that:
- **Claims are taken on trust.** Sonnet twice committed after re-running only part of a suite.
- **A lint error reached a merge.** The master gate caught it, so master was never red, but nothing upstream did.
- **The agent that writes the code also writes its tests and adjusts the old ones.**

The two times an agent read another agent's code, it found real bugs:
- Sonnet found that Codex's miner check read the labor setting wrongly (T-250).
- Codex found two failing cases in the WIP fix for T-211.

That is cheap evidence that review pays.

## 4. Process overhead

- **Cut-offs and resumes.** There are 26 WIP or parked commits. T-145 was resumed three times. Much of the orchestrator's time went on briefs, monitors and timed resumes. The owner's rule of 2026-10-15 (Claude only, at most two subagents at a time) removes most of this.
- **Rule churn.** Day and night hours, quota pools and exceptions changed often. Brief wording caused mistakes: "stop" was read as stop the whole run, and one brief allowed browser specs to change but not unit tests.
- **`docs/backlog.md` conflicted on almost every merge**, because every task edits the same file.
- **Paperwork.** 48 audit reports, 160 data files and 39 MB under `reports/`. Commit messages run to 40 lines. Closing a task means folding decisions into the spec, moving the work file and fixing links.
- **Incidents.**
  - About 20 fixes were merged without the browser suite, and the year-long playthrough broke unseen.
  - A red master was pushed once.
  - A bisect blamed the wrong task.
  - A subagent killed every node process on the machine.

  Each led to a new rule, which is good, but the rule list keeps growing.

## 5. What to change, in order

1. **Player-path scenarios, one per chain**: food, drink, crafts and forge, hospital, trade, defence, pasture. They start from commands only. Staging the output of the system under test is not allowed. A short list of chains shows what is covered.
2. **More invariants, checked in every scenario.** For example: no orphan reservation; no job blocked as "unreachable" for more than N ticks while a path exists; every container reachable; every item has a place. This catches the "never worked" class cheaply.
3. **Review every change under `src/` before merge**, by a second agent: Opus reviewing Sonnet's work, or the `/code-review` skill. It should focus on the seams, cleanup of reservations, and save/load, and should check each "expectation updated" claim.
4. **Gate only on figures whose noise is measured.** Long chaotic runs become reports, not pass/fail.
5. **Shorter gates.** Agents run the affected tests and e2e; the full `npm test` runs once, on master, before the push. The instrument runs only for simulation changes, as now.
6. **Fewer full-screen goldens.** Replace them with assertions about meaning (this line says X), or show the golden diff in review.
7. **Less paperwork.** Short commit bodies; only the orchestrator edits the backlog; a script does the closing ritual.
8. **Mark spec numbers that have never been measured**, and measure them before building on them.
