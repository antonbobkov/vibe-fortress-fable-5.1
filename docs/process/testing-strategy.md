# Testing Strategy

**Owner:** implementation · **Depends on:** [`../04-implementation/tooling.md`](../04-implementation/tooling.md), [`../04-implementation/acceptance-tests.md`](../04-implementation/acceptance-tests.md), [`../01-architecture/simulation-core.md`](../01-architecture/simulation-core.md), [agent-workflow.md](agent-workflow.md)

Agents cannot look at the screen. Every behavior must therefore be observable through readers, events, world hashes, cell buffers or DOM/canvas probes. This document defines the tiers, the runner, and the gate. It applies to every task, whatever its size: a fix, a feature or a refactoring adds or extends tests in the same commit as the code.

## Tiers

| Tier | Tool | Location | Runs on | Purpose |
|---|---|---|---|---|
| Unit | Vitest | `test/unit/**` | every commit | Pure rules (`rules/*.ts`), core data structures, loader validation, UI panels under `jsdom`, the scripts' own logic |
| Scenario | Vitest + headless runner | `test/scenarios/**` | every commit | The acceptance tests of `04-implementation/acceptance-tests.md`, one file per scenario id |
| Property | Vitest + `fast-check` | `test/property/**` | every commit | Invariants: fluid conservation, determinism under random command streams, save round-trip, label consistency |
| Golden | Vitest | `test/golden/**` | every commit | World hashes and cell buffers for fixed seeds; changes require an explicit update script |
| E2E | Playwright (Chromium headless) | `test/e2e/**` | tasks touching `render/`, `ui/`, `app/`; every gate; nightly in CI | The real app in a browser: boot, generate, embark, issue commands through the DOM/keyboard, read the cell buffer through a test hook, take screenshots for the gate report |
| Performance | Vitest, separate config | `test/perf/**` | tasks touching code that has a budget in `performance-budget.md`; every gate; nightly in CI | Tick budgets on the reference fortress, per-system budgets, and the long balance measurements |

The dev dependencies are the list in `tooling.md` § package.json; the tiers use `fast-check`, `@playwright/test`, `jsdom` (unit tests of `render/` and `ui/`) and `@vitest/coverage-v8` (coverage gates). Runtime dependencies: none.

Recipe behaviour is tested through the real loop: `test/unit/workshops/recipe-smoke.test.ts` runs every recipe once from order to `ItemCrafted`. Tests that call a producer's `onComplete` directly may check output arithmetic, but a scenario named in `acceptance-tests.md` must run the loop (orders, claims, hauling, work), not call internals.

## The scenario runner

`test/scenarios/runner.ts` implements the scenario spec of `simulation-core.md` § Headless mode as a superset (`world` generalizes `region`; `setup`, `run` and `expect` generalize `ticks` and `assertions`):

```ts
interface Scenario {
  id: string; milestone: 0|1|2|3|4|5|6|7|8;
  seed: string;
  world: 'flat-test' | 'generated' | { region: Partial<RegionRecord> };   // see "Worlds" below
  embark?: 'default' | 'none' | EmbarkSpec;                                // omitted = 'none': no dwarves (pure environment tests); 'default' = the Balanced preset
  systems?: () => GameSystem[];              // extra systems, registered before init; a factory, so every run gets fresh instances
  setup?: (w: TestWorld) => void;            // direct world edits before tick 0 (dig rooms, place items, spawn creatures) through TestWorld helpers
  commands?: { tick: number; command: Command }[];
  run: number | ((w: TestWorld) => void);    // ticks, or a driver that steps and asserts
  expect?: (w: TestWorld) => void;           // assertions after run
  timeoutMs?: number;                        // passed to vitest by the suite that runs the scenario; the default is the 60 s of vitest.config.ts
}
```

`TestWorld` wraps `World` with helpers that call only public APIs and the spawn API: `digRoom(x, y, z, w, h)`, `placeFloorSlab(...)`, `spawnDwarf(opts)`, `spawnCreature(species, at, faction)`, `spawnItem(type, material, at, count)`, `build(type, at, materialChoice)` (completes the build instantly through the same code path as the job, for setup only), `zone(type, tiles)`, `setNeed(id, need, value)`, `setSkill(id, skill, level)`, `forceWeather(state)`, `forceTemperature(tile, c)`, `events(type)` (all events of a type since tick 0), `hash()`, `step(n)`, `until(pred, maxTicks)`.

**Worlds.**

- `'flat-test'` is built by `buildFlatTestMap` (`src/app/headless.ts`), not by 03's generator. Every column follows the column rule of `algorithms/local-map-generation.md` § 3 with a flat height map: the walkable surface at z = 32, three soil levels over granite, and the Sea of Fire with its basalt rim and cap. There is no river, no lake and no cavern. The region it stands for is `FLAT_TEST_SPEC`: temperate grassland, `serene_vale`, peril 0, wealth 2, temper 0, igneous, relief 0, arrival from the north.
- `'generated'` is the standard world of the scenario seed, embarked at its first embarkable region in id order (`defaultRegionId`). Region id 0 is always sea, so "region 0 of a seed" means index 0 of the embarkable regions.
- `{ region }` is the flat-test region with the given fields in place of its own, generated by 03's local map generation and seeded from the scenario seed. Its elevation is 158 unless given, the elevation whose base surface is z = 32, like `flat-test`. A region that is given a peril above 0 and no traits has no traits.

**Stand-in systems.** The `core_*` scenarios test the core with no real system. They pass `systems`, a factory of stand-in systems that carry real ids (`test/scenarios/stand-in-systems.ts`).

Every scenario file (`<id>.scenario.ts`) exports one `Scenario`. `test/scenarios/index.test.ts` checks that each file's scenario id matches its name, and the suites `m0.test.ts` … `m8.test.ts` run them, grouped by their `milestone` so that they run in parallel. **Every scenario runs on every `npm test`, except the ones named in `test/scenarios/perf-tier.ts`, which run in the performance tier** (today only `three_years`; see § The long scenarios). `index.test.ts` checks that each name in that list is a scenario file with its perf test file, so a scenario leaves `npm test` only by being listed there. The `milestone` field records which build milestone introduced the scenario and decides only which suite runs it; a new scenario sets `milestone: 8`. A scenario that cannot pass because of a recorded contradiction carries a `todo` naming the `C-` id and is reported as todo; a player-path scenario whose chain fails carries the id of the task that records the fault ([player-paths.md](player-paths.md)).

Statistical scenarios (hit rates, quality distributions) run their trials inside one scenario with a fixed seed and assert against the tolerance in the acceptance table; they never use randomness outside the world's streams. Where a fresh standard-size world per trial would cost too much (its connectivity build alone is about 0.3 s), the trials build the same flat-test columns on a compact map with `buildFlatTestMap(registry, w, h)`: `tr_dig_room` digs its room once on the standard map, and measures the stone drop rate over 100 fresh 32 × 32 worlds, each with its own seed, one miner and the same shaft and room.

A scenario with dwarves that runs for more than a few days must feed them. With `embark: 'none'` the setup spawns drink and meals (`pl_cave_cycle`, `ws_masterwork`); otherwise the dwarves die of thirst before the thing under test happens. The bound of such a scenario allows for the pauses to eat, drink and sleep (`ws_masterwork`: 35,000 ticks for its 100 beds).

### Stepped-world catalog inventory

`test/scenarios/inventory.test.ts` runs the short scenarios with `recorder.ts` attached. It checks every command in `COMMAND_TYPES`, event in `EVENT_TYPES`, job type and building type against observed coverage or an explicit exception table in the test. A command counts only after acceptance; an event only after dispatch during a world step; a job on its delivered creation or completion; a building only when built. Scenario-specific completion assertions still apply. The observer follows every world used by a scenario, including compact trial worlds and loaded replacements, and restores its listeners and prototype wrappers afterwards. Recording consumes no RNG and leaves the world hash unchanged.

Exceptions name a concrete unit or property test that reaches the entry through a stepped world, an open backlog row, or the outside-tick emission of `WorldGenerated`. Every reason is nonempty, referenced test files exist, and task exceptions name open rows. Entries are named explicitly, so new catalog content needs new measured coverage or a checked exception. Removed catalog entries cannot remain exceptions. A missing producing path is filed as a task rather than implemented by the inventory.

The inventory excludes `core_calendar` (ten years), `td_schedule` (two years), `th_schedule` (three years), `th_warning` (two first-raid waits), `year_one` (one year), `homestead_year` (forty days and the wait for a birth), `three_years` (three years, performance tier), `descent` (the full multilevel fortress), `t195_train_needs` (thirty days), `defence_year` (three stages of a defence fortress), and the player-path scenarios (`pp_*`, weeks of a fortress each). Their own suites retain all assertions and execution. Short cases isolate their relevant rules: a real final cavern dig, a world starting near its first raid warning, the ramp and stair constructions, and clearing a workshop's blocked order to deliver its idle transition. A kiln's magma power has stepped coverage; recipes remain reserved for future glass in the workshop specification.

### The long scenarios

`year_one` plays a full first year on a script: the opening orders, a trade depot before the summer caravan, and a cave farm of dimcap on the soil level below the surface to carry the winter. It asserts only the rows of `balance.md` § Year-one expectation that follow from a rule: the two year-1 caravans inside their season-day window, no caravan in winter, none from the Mountainhome before spring of year 2, the two guaranteed immigration waves at their guaranteed size, no raid in a peril-0 region, the surface plot dormant in winter while the cave plot sows in every season, freezing only in the cold seasons, no dwarf death, and a hall larger than the seven who embarked. Everything else (the days of the caravans and waves, the population, the wealth, the harvests, the stocks) is printed as the balance table that the gate report carries. Events have no tick field, so the scenario stamps days with a world event subscriber during the run.

`homestead_year` (T-153) plays a 40-day homestead playthrough on a generated temperate grassland stream map (seed `homestead-year`). It exercises systems 08 Animals and 09 Foraging along with dependent artisan workshops. The scenario builds a pasture with grazers assigned, a kennel with animal training, slaughter and butchery, milking, shearing, egg laying and collection, farm plots with crops (flax, barley, turnip, hops), gathering, and artisan workshop orders (cheese, thread, cloth, tunic, leather boots, quiver, bow, bone bolts, hopped ale, flour, flax processing), asserting that every job type and ordered recipe completes, key animal events occur, and no dwarf dies and no animal starves while pasture has grass. Everything is read at the end of the forty days except the birth: conception is a daily roll, so the world then steps on with no command until the first `AnimalBorn`, for at most two of the dog's gestations and ten days more.
 
`descent` (T-154) plays a deep expedition on a generated standard-size igneous map (seed `descent`, wealth 3, peril 1). It exercises the late-game descent through both cavern layers down to the magma sea. Starting with a stocked surface fortress, the scenario digs stairwells and ramps to breach Cavern 1 and Cavern 2, asserts `CavernBreached` and `TilesDiscovered`, builds walls and doors to seal each breach, and stations a military squad ("Deep Guard") at the breach door. It continues digging to the deepsilver vein at z = 4, tests that designating deepsilver before `ConfirmDeepsilver` is rejected with `deepsilver_unconfirmed` and accepted after confirmation, mines five deepsilver tiles, asserts `DeepsilverMined`, `DeepStirred` (level 1), and `MonsterEmerged`. On the surface, it smelts deepsilver ore and forges a deepsilver dagger. At the magma sea, the squad eliminates the emergent hollow crawlers, a channel is dug opening into level 7 magma, a 9×3 workshop hall is hollowed, and three magma workshops (`magma_smelter`, `magma_forge`, `magma_kiln`) are constructed from granite blocks. It executes work orders in the magma smelter and magma forge with zero fuel consumed, asserts dwarves beside magma suffer no burn damage, and verifies the total fluid volume in the magma sea remains unchanged.

`three_years` runs one representative fortress for three years. It asserts the deterministic guarantees (the mood floors, the cap on positive thoughts, the population and wave caps, the invariants), the fixture's own rules (a trade at every visit, every ordered chain completed at least once), the food chain's outcome (no dwarf death from hunger or thirst, more than the seven founders at the end) and the flight bound, whose noise is measured; it prints the dwarf deaths by cause and the balance table, and writes its printed figures to `THREE_YEARS_OUT` (default `.vite/three-years.json`; the sweep's go to `THREE_YEARS_SEEDS_OUT`). It is a balance instrument, not a per-commit gate: at walking speed ×1.5 the fortress grows to about 43 dwarves and the run takes about 18 minutes, so it runs in the performance tier (`npm run test:perf`, `test/perf/three_years_main.test.ts`, through the same `runScenario`, with its `timeoutMs` of 2,400,000 and every assertion unchanged) and not in `npm test` (T-140). The `year_one` scenarios stay in `npm test`. The sweep over 20 seeds and perils 0, 2 and 4 is too slow for `npm test` and lives in the performance tier (`test/perf/three_years_seeds.test.ts`, beside `year_one_seeds`); a seed whose fortress dies out after the bootstrap ends early.

The three long-run harnesses (`three_years`, `three_years_seeds` and the mood instrument `mood_breakdown`) share one fortress, `test/scenarios/three_years_fortress.ts`, so that they measure the same thing. Its world is not `flat-test`, which has no ore, gems, flux, coal or trees and so cannot exercise the economy. It is a compact 48 × 48 map made by every stage of 03's local generation from a region spec: wealth 2, temperate forest, mixed geology, temper 0, relief 0, a brook from west to south, `serene_vale` at peril 0 and no traits at perils 2 and 4. The script plays as a player could: it spawns no item and edits no terrain, searches no seeds, picks building sites from the actual ground, burns the logs it fells for charcoal, digs its halls at z = 26 below the soil and mines the deposits through one shaft, requests an iron anvil from the caravan at the highest priority, and makes tools and military gear before export goods. Where the anvil comes in the wagon (perils 2 and 4), the founders' bedrooms, the hospital and the corridor to them are dug at the priority of the squad's kit, and the kit's ore is opened only once they are dug. It answers a threat warning, a raid, a spotted thief or a dangerous wild animal near the gate or a surface dwarf with the hearth alert, which locks the gate's two doors; a warning keeps the alert up until its party comes. An alert that has locked every dwarf outside the gate shelters nobody, so the script lifts it and raises the alert again only once a dwarf is below ground. An alert for wild animals alone, which a squad without three weapons does not hunt, is lifted after half a day, and wild animals alone raise none for a day after. The squad's dead are replaced only once the alert is down.

Deaths: `year_one`, every seed of `year_one_seeds` and the played-fortress behaviour test (`test/perf/played_behavior.test.ts`) assert that no dwarf dies. The three-year runs (the main scenario and the peril-0 seeds of the sweep) assert only that no dwarf dies of hunger or thirst, and print the dwarf deaths by cause: at peril 0 a wild animal can kill a dwarf, and which dwarf it reaches first turns on the job timeline. A dwarf dead of hunger or of thirst has the cause `starvation`. Deaths of tame animals and pets, and of other creatures, are counted and reported and are not asserted: a dead hostile can mean that combat worked.

The year-one scenario and the main three-year scenario run `checkInvariants` every 1,200 ticks and at the end; the peril-2 and peril-4 three-year sweep seeds do the same. The checker validates jobs and reservations, item and equipment ownership, containers, stock and wealth recounts, creature state, buildings, crops and parties. A creature standing on a tile that is burning is not reported as standing on an impassable tile: fire spreads under a creature that does not move (a downed animal), and 05 burns it there; a creature on a tile that anything else makes impassable (a building, deep water for a walker) is reported. Its stall and flee observations sample every tick, so a creature that walks or sleeps between daily checks is not mistaken for an unchanged creature. Observation never writes simulation state or consumes a random draw.

Every scenario that runs real systems (all but the `core_*` scenarios of stand-in systems) ends with four of the checker's invariants, which `runScenario` asserts after `expect`; the long fixtures that call `checkInvariants` (`year_one`, the three-year runs, the played-fortress tests) run the same four groups with the rest of the checker, every 1,200 ticks and at the end. (1) No reservation, claim or held job has a holder that is dead, gone or doing something else: a job whose worker is dead or has another job; an item reserved by a job that does not list it, or by a dwarf whose plan does not name it; an owner or assignee that is dead (a coffin reserved for a dwarf stays reserved after the dwarf dies); a patient's bed that the patient does not hold; a job held for more than a day, with no progress and no step of its worker, by a worker whose brain is not working (the brain moves a worker aside for flight, shelter, a patient's bed or a critical need without giving back a job that cannot be interrupted, and the job resumes, so only the day-long case is a fault); and an empty container that a job reserved among its inputs but that holds anything that is not one of the job's inputs. (2) No job stays blocked as `unreachable` for more than a day while a worker with its labor reaches one of its stand tiles, or while none of its stand tiles can be stood on although a tile beside its anchor is passable and reachable (a work tile that is a built chest's own tile). The job record has no block time, so the checker learns when a block began by sampling the board every 100 ticks (`observe` in the long fixtures, and the sampler that `runScenario` installs); a failed walk dates its own block by its retry tick. A scenario shorter than a day, or one whose game is replaced by a load, cannot show this fault. (3) Every built container that holds items, or lies in a stockpile or hospital zone and so offers slots, empty or not, has a tile at or beside it that a dwarf of the fortress reaches. (4) Every item has a place: a tile, a container, a living carrier, a wearer, or a building (an installed item belongs to the building that links it, or to the trap that holds it), and so does everything that the item lies in. The rest of the checker is not asserted at the end of the short scenarios, because many of them stage equipment, creatures and terrain by hand. A scenario that fails one of the four has found a fault: it carries the id of the task that records the fault as its `todo`, and the inventory run skips it (its catalog coverage then needs a stepped unit test named in the exception table).

The main three-year scenario saves and loads once in each year while a caravan is present, verifies the immediate hash, and continues its existing commands and assertions on the loaded game. Test-only event history, invariant observations and economy measurements continue across the load. A compact played-fortress test in the unit tier covers this replacement and subsequent deterministic progression at each of the three year boundaries; the full three-year scenario remains in the performance tier.

## Player-path scenarios

Most of the faults found by audits and long runs were features that worked system by system and never from end to end: a chest that was never stocked, wild animals that never spawned, a pasture test that passed only because of a bug ([the process review](../../reports/audits/2026-10-15-process-review.md)). Each scenario had staged the very state that the system under test was supposed to produce.

So every production chain has a **player-path scenario**. It starts from an embark and drives the game with player commands only: designate, build, set labors, place orders, assign zones. Its `setup` may not spawn the items, creatures or buildings that the chain itself produces or delivers; it may spawn only what a player could not obtain by command (the embark wagon, a caravan's arrival forced by its event). Wild animals stay on unless the chain is about something else and the scenario says why. The assertion is the chain's outcome as a player sees it: the meal eaten, the patient treated, the goods traded.

The chains and their scenarios are listed in [player-paths.md](player-paths.md). A new chain, or a change that adds a step to a chain, adds or extends its player-path scenario in the same task.

## What may be a gate

A figure gates a merge only when its noise has been measured: the spread of the figure under changes that only move the job timeline is known, and the bound is wider than that spread. Long chaotic runs (the browser year, the three-year fixture, the twenty-seed sweep) are reports: they print their figures and assert only invariants (stock and container accounting, the mood formula's floors, the population and wave caps) and outcomes that a timeline-only change trips rarely, if ever: "no hunger or thirst death" (none in the 19 annual-instrument cohort runs recorded since T-260) and "not wiped out" (a seed that had survived went extinct in 3 of the 20 cohort runs recorded since 2026-10-12, far more rarely than any floor on the living count). The annual instrument guards the sum of the living for this reason (§ Annual wildlife survival).

## Golden tests

- `test/golden/world-hashes.json`: `{ seed, size }` → hash of `WorldMap`; `{ seed, ticks }` → hash of the world after N ticks of `flat-test` with the default embark and no commands, for N in {0, 1000, 5000}.
- `test/golden/render/*.json`: cell buffers of the fortress viewport for `{ seed, z, camera }` at tick 0 and after a scripted command list (terrain, designations, buildings and items, fluids, farms, a raid), of the widget set, of each outside screen and modal dialog at its own size (`m8-screens`), and of the fortress screen with the sidebar open at 80 columns and at 100 columns (`m8-panels`). Every one of them is a layout smoke test: it shows that the screen is laid out as before and says nothing about whether its content is right.
- Update only through `npm run golden:update -- <name>`, which rewrites the file and prints the diff summary. The update goes in the same commit as the behaviour change that caused it, and the commit body has a paragraph that starts with `golden:` and explains which files changed and why.
- A task that is not meant to change behaviour (a refactoring, a documentation or tooling task) must leave every golden file byte-identical.
- A render golden shows that a screen changed, not that it is right, and it is regenerated by the agent that changed the screen. So a panel is never tested by a golden: what a panel says is tested by assertions about meaning (this row says X, this key does Y) in `test/unit/ui/`, and a new screen is tested the same way and gets a layout smoke golden only when the layout itself is the risk. The assertions for the panels are in `t332-panels-*.test.ts` and for the outside screens in `t332-screens-content.test.ts`. The reviewer reads the diff of every golden that moves (agent-workflow.md § Review).

## Property tests

| Property | Generator | Invariant |
|---|---|---|
| fluid conservation | random sealed basins, random initial levels, 500 steps | Σ levels constant; every tile settles: after 500 steps the only active tiles are isolated level-1 water tiles waiting to evaporate |
| determinism under commands | random valid command streams over 2,000 ticks, run twice | equal hashes every 100 ticks |
| save round-trip | random tick to save at during a scripted run | equal hash to the uninterrupted run |
| connectivity consistency | random wall placements/removals | `reachable(a, b)` equals BFS reachability for 50 random pairs |
| item accounting | random craft/haul/destroy streams and squad membership/equipment commands | `counts` equals a recount from entities |
| malformed command handling | field sweep and 40 deterministic random trials per command | no throw; known rejection reasons; no invariant findings; every 15 accepted commands saves and loads with equal hashes |
| mood bounds | random thought streams with needs met | mood ≥ 20 |

A command stream is drawn before it runs, so a generator cannot know the ids of the zones and buildings that earlier commands of the same stream will create. A generator for a command that names a stockpile, item, building or zone (`SetStockpileFilter`, `ForbidItem`, `CancelBuilding`, `RemoveZone`) draws a reference `{ $nth, of }`: the k-th living entity of that kind by ascending id, k modulo the count, 0 when there is none. The workshop generator setup includes an iron-filtered maintain order so that command round trips cover material filters. `resolveCommand` (`test/property/command-generators.ts`) resolves it against the world when the command is submitted. Both runs of a property resolve against identical worlds, so their streams stay equal. `PlaceBuilding` draws from the placements for which 14's ghost gives no reason in the world the stream starts from; `CreateZone` keeps the tiles of its rectangle that `zoneTileQualifies` accepts and no zone holds. A command that an earlier command has made invalid is refused identically in both runs.

The malformed-command sweep uses a short synthetic fortress with valid targets for harvesting, pasture assignment, taming and releasing item-caged creatures, unlinking a lever, hatch modes, releasing building-caged creatures, coffin assignment and trap modes. Each of these commands must also accept a valid control command; rejection-only coverage is insufficient. Stage the harvest control's mature crop after the setup waits, so ordinary automatic harvesting cannot consume it before the sweep starts. Each accepted command type is saved immediately before a simulation tick; its load and unsaved game must hash equally at the save and after every one of the next 50 ticks. The busy core save scenario also designates channels while paused before its save.

Single-rule scenarios may set `surfaceWildlife: 'none'` to isolate their supplied animals or staged casualties from unrelated natural arrivals. The test-world factory gives only system 08 the species-free ocean surface list; terrain, climate, plants, threats and manually supplied animals keep their ordinary behavior. `defence_year` sets it too, on its generated map: its assertions are about the traps, the gate, the trained squad and the raid it stages, and natural arrivals would decide them by which dwarf a boar kills. This option is not used by the full-year browser, year-one or three-year fortress fixtures. Ordinary test worlds exercise natural spawning in every season and year.

## E2E harness

The app exposes `window.__deepholm` in test builds only (`import.meta.env.MODE === 'test'`): `{ host, readers, cells(): CellBuffer, submit(cmd), setSpeed(n), step(n), screenshotName(name) }`, with helpers for driving and reading the screen (`text()`, `screen()`, `cellCenter(col, row)`, `key(key, shift?)`, `dwarves()`, `hash()`, `lastSaveId()`, `settled()`). `readers` is an object the app builds for the hook: the world's core readers (`map`, `entities`, `calendar`, `fortress`), `ui` (the live `UiState`, which is presentation state and belongs to no system, so `ReaderSet` has no such reader), `world` (the generated world's reader, when there is one), `items`, `buildings`, and `of(id)` for any other system's reader. Playwright tests drive the real UI (keys and clicks) and assert through `cells()` and readers; they never call `submit` except to set up state faster. Every e2e test also saves a screenshot to `reports/screenshots/<test>.png`. That folder is ignored by git; a screenshot is committed only when a gate report shows it (3 per gate maximum, downscaled).

E2E suite: `boot`, `generate-and-embark`, `designate-by-drag`, `build-and-stockpile`, `panels-open-and-close`, `quick-save-load`, `fluid-overlay`, `farm-plot-and-orders`, `military-and-alert`, `trade-session`, `save-load-settings`, `game-menu`, `export-import`, `labor-manager`, `drag-place`, `building-panel`, `retire-and-legend`, `embark-custom`, `animals-panel`, `panels-act`, `frame-loop-day` (starts the clock at 4× and asserts that the calendar advances by a day through the real frame loop, and nothing else), `full-year` (generates world `e2e-year`, filters the world map for peril 0, embarks on a `serene_vale` region if the seed has one and otherwise on a region of peril 0 and temper 0, plays a scripted first year, asserts the same rule-based rows as the `year_one` scenario and reports the balance rows), `boot-dist` (`boot` against the built output). A task that adds a screen or a multi-step interaction adds or extends a spec here.

`full-year` is deterministic: the fortress opens paused and the spec gives every UI command with the clock paused, so that a command applies on the tick it is given (a stockpile or farm plot it has just made is opened after one `step(1)`), and time advances only through the hook's `step`. Real time then cannot change the year, and two runs of one commit print the same end state, with the same world hash. The frame loop is `frame-loop-day`'s concern alone.

The playthrough answers wildlife through the UI at simulation tick boundaries. It forms a squad of three during the opening after day 3, before advancing to day 10, and starts the wildlife response after day 20. It looks every 20 ticks: an aggressive predator within 40 horizontal tiles of the wagon raises watchful; an unconsumed wild attack on a fortress creature raises hearth when the cooldown permits. Hearth lasts at least 300 ticks and ends only when no predator is near, returning to watchful. After leaving hearth it waits 1,500 ticks before another hearth alert. With no predator currently near and the last recorded threat at least 600 ticks old, watchful returns to calm. Critical needs may take a sheltering civilian out to eat or drink and back, per 10 and 19.

The end-state line lists every fortress-creature death with its day, cause and killer species. The browser asserts that the fortress is not wiped out and no dwarf death from hunger or thirst. It prints the living count, the Starving events, the food and drink stocks against ten days and the rest of the end state: between recorded runs of the annual instrument one seed's living moved by five or more, and its year-end food or drink by four fifths. Annual wildlife balance is measured over multiple seeds by the performance instrument below.

`zones-editor` configures a stockpile's preset, category tree, container counts, priority, quality and material classes through keyboard and mouse while paused. It also assigns and clears a bedroom owner through the shared picker, checks missing-bed and open-border messages, and asserts that the calendar did not advance.

The caravan exchange harness acknowledges any danger announcement from the wait for arrival before issuing its panel keys; the trade assertions then run through the ordinary controls.

E2E starts a test-mode development server and a separate static server (Vite preview) for a test-mode build of `dist/`. `boot-dist` runs against the second the same assertions that `boot` runs against the first (`test/e2e/boot-smoke.ts`), so the built output is tested without putting the hook into a production build. Production builds omit `window.__deepholm`: run `npm run build` after the e2e suite to restore production output.

## Coverage gates

Vitest coverage (`@vitest/coverage-v8`) thresholds, enforced whenever the tests run with `--coverage`, which every gate does: `src/core` 90% lines, `src/systems/**/rules` 90%, `src/systems/**` 75%, `src/render` 60%, `src/ui` 50%. Thresholds are set per glob in `vitest.config.ts`, with no global threshold, and are raised, never lowered. `src/platform`, `src/app` and `src/content` have no threshold: the gate report shows their coverage and does not gate on it. The IndexedDB adapter of `src/platform/storage.ts` cannot run under Node; the save and load e2e specs exercise it in the browser.

## Performance smoke

The tier measures three saved fortresses, because they are different workloads. `test/fixtures/reference-fortress.deepholm` is the reference fortress of `performance-budget.md` (80 dwarves, year three): the load of the budget's reference scenario with a settlement on it, built by `test/perf/scripted-reference.ts`: every workshop that has recipes (twelve with a standing order), six farm plots with crops and seeds, food, drink and a still, two squads of six with a barracks each, a hospital, a trade depot, a gate with a door set to lock on alert, a drawbridge on a lever and four cage traps, ten 5×5 stockpiles (three of them for drink, in barrels) with the presets a played fortress uses, and labors set by profession templates. `test/fixtures/reference-fortress-furniture.deepholm` is the first 80-dwarf fixture (the same map, channel, cavern, dwarves, animals and 25,000 items, with 600 pieces of furniture and 60 small zones, and no workshop, farm, squad, depot or gate); it is kept so that the budgets measured on it keep their meaning. `test/fixtures/played-fortress.deepholm` is a 20-dwarf fortress that a script played for 4,200 ticks. `perf_reference.test.ts` holds the played fortress to every system's allocation (pathing ≤ 1.0 ms, core ≤ 0.30 ms, worst tick ≤ 40 ms), and the furniture fixture to an average tick ≤ 12 ms and a worst tick ≤ 40 ms. `per-system.test.ts` holds each system on the furniture fixture to twice its allocation. `reference_fortress.test.ts` lists what the reference fortress contains (counts of workshops, orders, plots, squads, the depot, the gate, the stockpiles, the labor sets). `reference_fortress_figures.test.ts` reports the per-system figures of the reference fortress, which gate nothing, and lets it live through a season with nobody dying of hunger or thirst. `played_behavior.test.ts` checks that the played fortress behaves (dwarves alive, the disturbed lake settles, orders and hauling run). The tier also holds the long measurements that are too slow for `npm test` (the main `three_years` scenario, the 20-seed three-year sweep, the mood instrument). It runs at every gate (unless the gate is run with `--no-perf`), nightly in CI, and for any task that touches budgeted code. It takes about 40 minutes, and about an hour with the season of the reference fortress.

Each three-year sweep seed prints its final `{ seed, peril, tick, hash }` record. A full gate records those hashes and compares equal seed, peril and tick records with the most recently recorded gate that contains them. The report distinguishes equal hashes, changed hashes and absent comparable baselines. A changed hash needs review against intervening behavior or fixture changes; a gate without the performance tier reports that no comparison was made. Frozen prior reports are read, never rewritten.

A creature with no Position is valid only while caged or, for a tame animal stolen by a thief, while the party loot and animal-carrier mapping identify a living member with a position and the matching Hostile party id. An absent, mismatched or dead carrier still violates the creature-position invariant.

The test-world `spawnTame` helper accepts an explicit `trained` state for guard fixtures; omitted training remains `none`.

### Annual wildlife survival

`test/perf/wildlife_year.test.ts` runs twelve distinct seeds, four each in temperate forest, taiga and temperate grassland, on standard-size generated local maps at peril 0. It uses Balanced embark and the browser opening's command schedule, work-order targets, farm rectangles, three-member squad and wildlife response. The controlled regions have a west arrival, temper 0, wealth 2 and no traits that suppress natural wildlife. The dimcap plot keeps its 32-tile rectangle on the deepest soil floor at most two levels below the surface, so taiga's two soil layers use one level down. Surface plots use the same green-tile selection as the browser, and their actual qualifying area is recorded for each seed. There are no added supplies, farms or prebuilt defences.

Record living and total arrivals, every dwarf and fortress-animal death with tick, day, cause and killer, Starving events, natural spawns, alerts, food stocks, harvests, hunts and the final world hash. Stop an extinct fortress at its next observation boundary. Report overall and per-biome median, minimum, extinction count and share of seeds without a wildlife dwarf death. The target and measured bounds are stated in [the balance model](../03-content/balance.md#wild-animals). Persist each completed seed and the final distribution even when a bound fails. Re-run this distribution before and after changes to wildlife, fleeing, alerts, treatment or needs; record both rows in the commit body.

The guarded figures are the median, the sum of the living over the twelve years, wildlife-free years, extinctions and hunger/thirst deaths. Their bounds are computed from the best measured figures: median minus one dwarf, sum of the living minus twelve dwarves, wildlife-free minus two seeds, extinction count plus one fortress, and hunger/thirst deaths plus one. Always report the worst and the second-worst seed, but do not guard a single seed: one fortress's year turns on which dwarf an animal reaches first, and changes that only move the job timeline shift single seeds by five or more living in both directions while the sum moves by less than ten. Block a change when any bound fails or when three or more of the five guarded figures worsen together, even within their tolerances. Compare simultaneous worsening against the latest accepted before row, so an earlier tolerated drop is not counted again on a later change. Keep that latest actual row alongside the best figures used for the bounds; update the row and every improved measured figure in the same commit, retaining earlier better bounds when a tolerant figure falls. Always record the actual before and after rows. The survival targets remain unchanged.

When a seed changes outcome class (extinct or surviving), or changes by five or more living, under a change that only moves the job timeline, name it as unstable in the commit body and retain the seed in the living balance status. The cohort stays at twelve seeds, which is what a behaviour change can afford to run; the sum of the living is the guard that unstable seeds cannot flip alone. The seed records, the worst and the second-worst outcome remain in every measurement.

## The docs link check

`scripts/docs-links-check.mjs` reads every Markdown file under `docs/`, `reports/` and `agents/`, and the root `README.md`. It fails on an inline link or image whose relative target does not exist. It skips URLs, in-page anchors, fenced code and inline code, and it does not resolve the heading after a `#`. A task that moves or renames a document fixes every link to it in the same commit; the check is how it finds them. `test/unit/docs-links-check.test.ts` runs the same check, so `npm test` fails on a broken link too.

## Test naming

`describe('T-123 designations', ...)` for unit tests, with the id of the task that adds them; scenario ids as file names (`tr_dig_room.scenario.ts`). A test that pins a choice made under the [ambiguity protocol](ambiguity-protocol.md) says in its name what it pins; one that pins a decision-log row or a contradiction names the row: `it('D-007: ...')`, `it.todo('C-nnn: ...')`. Existing tests keep the labels they were written with (`T-M1-03`, `F-12`, `U-03`).
