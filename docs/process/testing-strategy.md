# Testing Strategy

**Owner:** implementation · **Depends on:** [`../04-implementation/tooling.md`](../04-implementation/tooling.md), [`../04-implementation/acceptance-tests.md`](../04-implementation/acceptance-tests.md), [`../01-architecture/simulation-core.md`](../01-architecture/simulation-core.md), [agent-workflow.md](agent-workflow.md)

Agents cannot look at the screen. Every behavior must therefore be observable through readers, events, world hashes, cell buffers or DOM/canvas probes. This document defines the tiers, the runner, and the gate. It applies to every task, whatever its size: a fix, a feature or a refactoring adds or extends tests in the same commit as the code.

## Tiers

| Tier | Tool | Location | Runs on | Purpose |
|---|---|---|---|---|
| Unit | Vitest | `test/unit/**` | every commit | Pure rules (`rules/*.ts`), core data structures, loader validation, UI panels under `jsdom`, the scripts' own logic |
| Scenario | Vitest + headless runner | `test/scenarios/**` | every commit | The acceptance tests of `04-implementation/acceptance-tests.md`, one file per scenario id |
| Property | Vitest + `fast-check` | `test/property/**` | every commit | Invariants: fluid conservation, determinism under random command streams, save round-trip, label consistency |
| Golden | Vitest | `test/golden/**` | every commit | World hashes and cell buffers for fixed seeds; changes require an explicit update script |
| E2E | Playwright (Chromium headless) | `test/e2e/**` | tasks touching `render/`, `ui/`, `app/`; every gate; on demand in CI | The real app in a browser: boot, generate, embark, issue commands through the DOM/keyboard, read the cell buffer through a test hook, take screenshots for the gate report |
| Performance | Vitest, separate config | `test/perf/**` | tasks touching code that has a budget in `performance-budget.md`; every gate; on demand in CI (`measure.yml`) | Tick budgets on the reference fortress, per-system budgets, and the long balance measurements |

The dev dependencies are the list in `tooling.md` § package.json; the tiers use `fast-check`, `@playwright/test`, `jsdom` (unit tests of `render/` and `ui/`) and `@vitest/coverage-v8` (coverage gates). Runtime dependencies: none.

Recipe behaviour is tested through the real loop: `test/unit/workshops/recipe-smoke.test.ts` runs every recipe once from order to `ItemCrafted`. Tests that call a producer's `onComplete` directly may check output arithmetic, but a scenario named in `acceptance-tests.md` must run the loop (orders, claims, hauling, work), not call internals.

## The scenario runner

`test/scenarios/runner.ts` implements the scenario spec of `simulation-core.md` § Headless mode as a superset (`world` generalizes `region`; `setup`, `run` and `expect` generalize `ticks` and `assertions`):

```ts
interface Scenario {
  id: string; milestone: 0|1|2|3|4|5|6|7|8;
  seed: string;
  world: 'flat-test' | 'generated' | { region: Partial<RegionRecord> };   // see "Worlds" below
  embark?: 'default' | 'none' | EmbarkSpec;                                // omitted = 'none': no dwarves (pure environment tests); 'default' = the Balanced preset
  systems?: () => GameSystem[];              // extra systems, registered before init; a factory, so every run gets fresh instances
  setup?: (w: TestWorld) => void;            // direct world edits before tick 0 (dig rooms, place items, spawn creatures) through TestWorld helpers
  commands?: { tick: number; command: Command }[];
  run: number | ((w: TestWorld) => void);    // ticks, or a driver that steps and asserts
  expect?: (w: TestWorld) => void;           // assertions after run
  timeoutMs?: number;                        // passed to vitest by the suite that runs the scenario; the default is the 60 s of vitest.config.ts
}
```

`TestWorld` wraps `World` with helpers that call only public APIs and the spawn API: `digRoom(x, y, z, w, h)`, `placeFloorSlab(...)`, `spawnDwarf(opts)`, `spawnCreature(species, at, faction)`, `spawnItem(type, material, at, count)`, `build(type, at, materialChoice)` (completes the build instantly through the same code path as the job, for setup only), `zone(type, tiles)`, `setNeed(id, need, value)`, `setSkill(id, skill, level)`, `forceWeather(state)`, `forceTemperature(tile, c)`, `events(type)` (all events of a type since tick 0), `hash()`, `step(n)`, `until(pred, maxTicks)`.

**Worlds.**

- `'flat-test'` is built by `buildFlatTestMap` (`src/app/headless.ts`), not by 03's generator. Every column follows the column rule of `algorithms/local-map-generation.md` § 3 with a flat height map: the walkable surface at z = 32, three soil levels over granite, and the Sea of Fire with its basalt rim and cap. There is no river, no lake and no cavern. The region it stands for is `FLAT_TEST_SPEC`: temperate grassland, `serene_vale`, peril 0, wealth 2, temper 0, igneous, relief 0, arrival from the north.
- `'generated'` is the standard world of the scenario seed, embarked at its first embarkable region in id order (`defaultRegionId`). Region id 0 is always sea, so "region 0 of a seed" means index 0 of the embarkable regions.
- `{ region }` is the flat-test region with the given fields in place of its own, generated by 03's local map generation and seeded from the scenario seed. Its elevation is 158 unless given, the elevation whose base surface is z = 32, like `flat-test`. A region that is given a peril above 0 and no traits has no traits.

**Stand-in systems.** The `core_*` scenarios test the core with no real system. They pass `systems`, a factory of stand-in systems that carry real ids (`test/scenarios/stand-in-systems.ts`).

Every scenario file (`<id>.scenario.ts`) exports one `Scenario`. `test/scenarios/index.test.ts` checks that each file's scenario id matches its name, and the suites `m0.test.ts` … `m8.test.ts` run them, grouped by their `milestone` so that they run in parallel. **Every scenario runs on every `npm test`, except the ones named in `test/scenarios/perf-tier.ts`, which run in the performance tier** (today only `three_years`; see § The long scenarios). `index.test.ts` checks that each name in that list is a scenario file with its perf test file, so a scenario leaves `npm test` only by being listed there. The `milestone` field records which build milestone introduced the scenario and decides only which suite runs it; a new scenario sets `milestone: 8`. A scenario that cannot pass because of a recorded contradiction carries a `todo` naming the `C-` id and is reported as todo; a player-path scenario whose chain fails carries the id of the task that records the fault ([player-paths.md](player-paths.md)).

Statistical scenarios (hit rates, quality distributions) run their trials inside one scenario with a fixed seed and assert against the tolerance in the acceptance table; they never use randomness outside the world's streams. Where a fresh standard-size world per trial would cost too much (its connectivity build alone is about 0.3 s), the trials build the same flat-test columns on a compact map with `buildFlatTestMap(registry, w, h)`: `tr_dig_room` digs its room once on the standard map, and measures the stone drop rate over 100 fresh 32 × 32 worlds, each with its own seed, one miner and the same shaft and room.

A scenario with dwarves that runs for more than a few days must feed them. With `embark: 'none'` the setup spawns drink and meals (`pl_cave_cycle`, `ws_masterwork`); otherwise the dwarves die of thirst before the thing under test happens. The bound of such a scenario allows for the pauses to eat, drink and sleep (`ws_masterwork`: 35,000 ticks for its 100 beds).

### Stepped-world catalog inventory

`test/scenarios/inventory.test.ts` runs the short scenarios with `recorder.ts` attached. It checks every command in `COMMAND_TYPES`, event in `EVENT_TYPES`, job type and building type against observed coverage or an explicit exception table in the test. A command counts only after acceptance; an event only after dispatch during a world step; a job on its delivered creation or completion; a building only when built. Scenario-specific completion assertions still apply. The observer follows every world used by a scenario, including compact trial worlds and loaded replacements, and restores its listeners and prototype wrappers afterwards. Recording consumes no RNG and leaves the world hash unchanged.

Exceptions name a concrete unit or property test that reaches the entry through a stepped world, an open backlog row, or the outside-tick emission of `WorldGenerated`. Every reason is nonempty, referenced test files exist, and task exceptions name open rows. Entries are named explicitly, so new catalog content needs new measured coverage or a checked exception. Removed catalog entries cannot remain exceptions. A missing producing path is filed as a task rather than implemented by the inventory.

The inventory excludes `core_calendar` (ten years), `td_schedule` (two years), `th_schedule` (three years), `th_warning` (two first-raid waits), `year_one` (one year), `homestead_year` (forty days and the wait for a birth), `three_years` (three years, performance tier), `descent` (the full multilevel fortress), `t195_train_needs` (thirty days), `defence_year` (two years of a defence fortress), and the player-path scenarios (`pp_*`, weeks of a fortress each). Their own suites retain all assertions and execution. Short cases isolate their relevant rules: a real final cavern dig, a world starting near its first raid warning, the ramp and stair constructions, and clearing a workshop's blocked order to deliver its idle transition. A kiln's magma power has stepped coverage; recipes remain reserved for future glass in the workshop specification.

### The long scenarios

`year_one` plays a full first year on a script: the opening orders, a trade depot before the summer caravan, and a cave farm of dimcap on the soil level below the surface to carry the winter. It asserts only the rows of `balance.md` § Year-one expectation that follow from a rule: the two year-1 caravans inside their season-day window, no caravan in winter, none from the Mountainhome before spring of year 2, the two guaranteed immigration waves at their guaranteed size, no raid in a peril-0 region, the surface plot dormant in winter while the cave plot sows in every season, freezing only in the cold seasons, no dwarf death, and a hall larger than the seven who embarked. It also asserts two steps of its own script: a completed trade with the Hillfolk at the depot (the founders quarry stone below the hall for its blocks and send the spare stone as cargo), and a save made at the start of day 56 that loads into a second world with the same hash and plays that day to the same hash as the first. Everything else (the days of the caravans and waves, the population, the wealth, the harvests, the stocks) is printed as the balance table that the gate report carries. Events have no tick field, so the scenario stamps days with a world event subscriber during the run.

`homestead_year` (T-153) plays a 40-day homestead playthrough on a generated temperate grassland stream map (seed `homestead-year`). It exercises systems 08 Animals and 09 Foraging along with dependent artisan workshops. The scenario builds a pasture with grazers assigned, a kennel with animal training, slaughter and butchery, milking, shearing, egg laying and collection, farm plots with crops (flax, barley, turnip, hops), gathering, and artisan workshop orders (cheese, thread, cloth, tunic, leather boots, quiver, bow, bone bolts, hopped ale, flour, flax processing), asserting that every job type and ordered recipe completes, key animal events occur, and no dwarf dies and no animal starves while pasture has grass. Everything is read at the end of the forty days except the birth: conception is a daily roll, so the world then steps on with no command until the first `AnimalBorn`, for at most two of the dog's gestations and ten days more.
 
`descent` (T-154) plays a deep expedition on a generated standard-size igneous map (seed `descent`, wealth 3, peril 1). It exercises the late-game descent through both cavern layers down to the magma sea. Starting with a stocked surface fortress, the scenario digs stairwells and ramps to breach Cavern 1 and Cavern 2, asserts `CavernBreached` and `TilesDiscovered`, builds walls and doors to seal each breach, and stations a military squad ("Deep Guard") at the breach door. It continues digging to the deepsilver vein at z = 4, tests that designating deepsilver before `ConfirmDeepsilver` is rejected with `deepsilver_unconfirmed` and accepted after confirmation, mines five deepsilver tiles, asserts `DeepsilverMined`, `DeepStirred` (level 1), and `MonsterEmerged`. On the surface, it smelts deepsilver ore and forges a deepsilver dagger. At the magma sea, the squad eliminates the emergent hollow crawlers, a channel is dug opening into level 7 magma, a 9×3 workshop hall is hollowed, and three magma workshops (`magma_smelter`, `magma_forge`, `magma_kiln`) are constructed from granite blocks. It executes work orders in the magma smelter and magma forge with zero fuel consumed, asserts dwarves beside magma suffer no burn damage, and verifies the total fluid volume in the magma sea remains unchanged.

`three_years` runs one representative fortress for three years, on the fixture's own ground (relief 1), seed `three-years-p0-3`: a peril-0 seed of the sweep that grows at every shift. ## Player-path scenarios

Most of the faults found by audits and long runs were features that worked system by system and never from end to end: a chest that was never stocked, wild animals that never spawned, a pasture test that passed only because of a bug ([the process review](../../reports/audits/2026-10-15-process-review.md)). Each scenario had staged the very state that the system under test was supposed to produce.

So every production chain has a **player-path scenario**. It starts from an embark and drives the game with player commands only: designate, build, set labors, place orders, assign zones. Its `setup` may not spawn the items, creatures or buildings that the chain itself produces or delivers; it may spawn only what a player could not obtain by command (the embark wagon, a caravan's arrival forced by its event). Wild animals stay on unless the chain is about something else and the scenario says why. The assertion is the chain's outcome as a player sees it: the meal eaten, the patient treated, the goods traded.

The chains and their scenarios are listed in [player-paths.md](player-paths.md). A new chain, or a change that adds a step to a chain, adds or extends its player-path scenario in the same task.

## What may be a gate

A figure gates a merge only when its noise has been measured: the spread of the figure under changes that only move the job timeline is known, and the bound is wider than that spread. Long chaotic runs (the browser year, the three-year fixture, the twenty-seed sweep) are reports: they print their figures and assert only invariants (stock and container accounting, the mood formula's floors, the population and wave caps) and outcomes that a timeline-only change trips rarely, if ever: "no hunger or thirst death" (none in the 19 annual-instrument cohort runs recorded from T-260 to T-482; one in the 12 shifts T-509 measured, a fault of the instrument's opening that T-509 fixed) and "not wiped out" (a seed that had survived went extinct in 3 of the 20 cohort runs recorded since 2026-10-12, far more rarely than any floor on the living count). The annual instrument guards the sum of the living for this reason, and judges it over eight shifted samples because one sample's spread is wider than any useful bound (§ Annual wildlife survival). In `three_years_seeds` survival and hunger at peril 0 are rules over the whole set, not over each seed, since a single seed's outcome flips under changes that do not aim at it, and they are judged over four shifted sweeps, since one sweep's set figures flip too (§ The twenty-seed sweep). Each seed prints its year-1 population, its growth and its deaths from hunger or thirst; its invariants and witnesses stay asserted one by one. Each seed also prints how crowded its door, hearth-hall and squad station tiles were and for how long (`test/scenarios/crowd-watch.ts`), the hostiles dead, what killed its dwarves and how often a hostile passed someone in a doorway (`test/scenarios/party-watch.ts`). Two seeds were exempt by name before the set rule and may spend its allowance again: `three-years-p4-2`'s year 1 (a day-37 fire burns every medic and the day-67 raid finishes the rest; it flipped four times in six commits on 2026-10-21 and 22, [bisection](../../reports/audits/2026-10-22-p4-2-year-one.md), [trial](../../reports/audits/2026-10-22-infection-roll-per-dwarf.md)), and `three-years-p0-2`'s growth (two boars settle by its gate in year 3, and a flight rule moved it between 15 dwarves and none, [bisection](../../reports/audits/2026-10-22-p0-2-three-years.md), [boars](../../reports/audits/2026-10-22-boars-maul-p0-2.md)). A rise in what the allowance has to cover is a finding to report, not a bound to widen.

## Golden tests

- `test/golden/world-hashes.json`: `{ seed, size }` → hash of `WorldMap`; `{ seed, ticks }` → hash of the world after N ticks of `flat-test` with the default embark and no commands, for N in {0, 1000, 5000}.
- `test/golden/render/*.json`: cell buffers of the fortress viewport for `{ seed, z, camera }` at tick 0 and after a scripted command list (terrain, designations, buildings and items, fluids, farms, a raid), of the widget set, of each outside screen and modal dialog at its own size (`m8-screens`), and of the fortress screen with the sidebar open at 80 columns and at 100 columns (`m8-panels`). Every one of them is a layout smoke test: it shows that the screen is laid out as before and says nothing about whether its content is right.
- Update only through `npm run golden:update -- <name>`, which rewrites the file and prints the diff summary. The update goes in the same commit as the behaviour change that caused it, and the commit body has a paragraph that starts with `golden:` and explains which files changed and why.
- A task that is not meant to change behaviour (a refactoring, a documentation or tooling task) must leave every golden file byte-identical.
- A render golden shows that a screen changed, not that it is right, and it is regenerated by the agent that changed the screen. So a panel is never tested by a golden: what a panel says is tested by assertions about meaning (this row says X, this key does Y) in `test/unit/ui/`, and a new screen is tested the same way and gets a layout smoke golden only when the layout itself is the risk. The assertions for the panels are in `t332-panels-*.test.ts` and for the outside screens in `t332-screens-content.test.ts`. The reviewer reads the diff of every golden that moves (agent-workflow.md § Review).

## Property tests

| Property | Generator | Invariant |
|---|---|---|
| fluid conservation | random sealed basins, random initial levels, 500 steps | Σ levels constant; every tile settles: after 500 steps the only active tiles are isolated level-1 water tiles waiting to evaporate |
| determinism under commands | random valid command streams over 2,000 ticks, run twice | equal hashes every 100 ticks |
| save round-trip | random tick to save at during a scripted run | equal hash to the uninterrupted run |
| connectivity consistency | random wall placements/removals | `reachable(a, b)` equals BFS reachability for 50 random pairs |
| item accounting | random craft/haul/destroy streams and squad membership/equipment commands | `counts` equals a recount from entities |
| malformed command handling | field sweep and 40 deterministic random trials per command | no throw; known rejection reasons; no invariant findings; every 15 accepted commands saves and loads with equal hashes |
| mood bounds | random thought streams with needs met | mood ≥ 20 |

A command stream is drawn before it runs, so a generator cannot know the ids of the zones and buildings that earlier commands of the same stream will create. A generator for a command that names a stockpile, item, building or zone (`SetStockpileFilter`, `ForbidItem`, `CancelBuilding`, `RemoveZone`) draws a reference `{ $nth, of }`: the k-th living entity of that kind by ascending id, k modulo the count, 0 when there is none. The workshop generator setup includes an iron-filtered maintain order so that command round trips cover material filters. `resolveCommand` (`test/property/command-generators.ts`) resolves it against the world when the command is submitted. Both runs of a property resolve against identical worlds, so their streams stay equal. `PlaceBuilding` draws from the placements for which 14's ghost gives no reason in the world the stream starts from; `CreateZone` keeps the tiles of its rectangle that `zoneTileQualifies` accepts and no zone holds. A command that an earlier command has made invalid is refused identically in both runs.

The malformed-command sweep uses a short synthetic fortress with valid targets for harvesting, pasture assignment, taming and releasing item-caged creatures, unlinking a lever, hatch modes, releasing building-caged creatures, coffin assignment and trap modes. Each of these commands must also accept a valid control command; rejection-only coverage is insufficient. Stage the harvest control's mature crop after the setup waits, so ordinary automatic harvesting cannot consume it before the sweep starts. Each accepted command type is saved immediately before a simulation tick; its load and unsaved game must hash equally at the save and after every one of the next 50 ticks. The busy core save scenario also designates channels while paused before its save.

Single-rule scenarios may set `surfaceWildlife: 'none'` to isolate their supplied animals or staged casualties from unrelated natural arrivals. The test-world factory gives only system 08 the species-free ocean surface list; terrain, climate, plants, threats and manually supplied animals keep their ordinary behavior. `defence_year` sets it too, on its generated map: its assertions are about the traps, the gate, the trained squad and the parties 18 sends, and natural arrivals would decide them by which dwarf a boar kills. This option is not used by the full-year browser, year-one or three-year fortress fixtures. Ordinary test worlds exercise natural spawning in every season and year.

Its worst tick is the largest of each tick's least time over three passes of the same 2,000 ticks, whose noise is measured (`performance-budget.md` § Measurement); the single-pass worst is held to a loose 80 ms, for a stall that comes once. `per-system.test.ts` holds each system on the furniture fixture to twice its allocation. `reference_fortress.test.ts` lists what the reference fortress contains (counts of workshops, orders, plots, squads, the depot, the gate, the stockpiles, the labor sets). `reference_fortress_figures.test.ts` reports the per-system figures of the reference fortress, which gate nothing, and lets it live through a season with nobody dying of hunger or thirst. `played_behavior.test.ts` checks that the played fortress behaves (no dwarf dead but in a fight, the disturbed lake settles, orders and hauling run). The tier also holds the long measurements that are too slow for `npm test` (the main `three_years` scenario, the 20-seed three-year sweep, the mood instrument). It runs at every gate (unless the gate is run with `--no-perf`), nightly in CI, and for any task that touches budgeted code. It takes about 40 minutes, and about an hour with the season of the reference fortress.

Each three-year sweep seed prints its final `{ seed, peril, tick, hash }` record. A full gate records those hashes and compares equal seed, peril and tick records with the most recently recorded gate that contains them. The report distinguishes equal hashes, changed hashes and absent comparable baselines. A changed hash needs review against intervening behavior or fixture changes; a gate without the performance tier reports that no comparison was made. Frozen prior reports are read, never rewritten.

### Annual wildlife survival

`test/perf/wildlife_year.test.ts` runs twelve distinct seeds, four each in temperate forest, taiga and temperate grassland, on standard-size generated local maps at peril 0. It uses Balanced embark and the browser opening's command schedule, work-order targets, farm rectangles, three-member squad and wildlife response. The controlled regions have a west arrival, temper 0, wealth 2 and no traits that suppress natural wildlife. The dimcap plot keeps its 32-tile rectangle on the deepest soil floor at most two levels below the surface, so taiga's two soil layers use one level down. Surface plots use the same green-tile selection as the browser, and their actual qualifying area is recorded for each seed. Where the camp window lacks level ground for the workshops at the wagon's level, the remaining sites are the nearest by walk from the camp's stockpile, on the wagon's level or up to two levels above or below it, and their walking distances are recorded. No zone is drawn over the wagon, another building or a chosen workshop site. The rock the opening digs drops a stone from 30% of its tiles, so how many stones it yields moves with the timeline; when a building of the opening has waited two days for stone or blocks, with no raw stone about and nothing left to dig, the player digs the next 5 by 5 room of rock beside the lower room, at most three rooms, and the days are recorded (T-509: without it, taiga seed 3's kitchen waited all year in one timeline and grassland seeds 3 and 4 had no hearth in 7 of 16 timelines each). There are no added supplies, farms or prebuilt defences.

Record living and total arrivals, every dwarf and fortress-animal death with tick, day, cause and killer, Starving events, natural spawns, alerts, food stocks, harvests, hunts and the final world hash. Stop an extinct fortress at its next observation boundary. Report overall and per-biome median, minimum, extinction count and share of seeds without a wildlife dwarf death. The target and measured bounds are stated in [the balance model](../03-content/balance.md#wild-animals). Persist each completed seed and the final distribution. Re-run the instrument before and after changes to wildlife, fleeing, alerts, treatment or needs; record both pooled rows in the commit body.

**A change is judged over eight samples, never one** (T-509). The same code shifted a few ticks before the opening plays a different year: on master at T-482 and T-486, twelve such shifts moved the sum of the living between 118 and 157, the median between 10.5 and 13 and wildlife-free years between 6 and 10, and 4 of the 12 failed the bounds a single sample was then held to ([measurement](../../reports/audits/2026-11-05-t509-instrument-noise.md)). So `measure.yml`'s `instrument` suite plays the instrument eight times in parallel, the same commit shifted 0 to 7 ticks (`WILDLIFE_YEAR_SHIFT`; `WILDLIFE_SAMPLES` is 8), and its verdict job (`test/perf/wildlife_year_verdict.test.ts`) pools them: the median, the sum of the living, wildlife-free years, the worst and the second-worst are means over the eight samples; extinct years, starved years (a year with a dwarf dead of hunger or thirst) and need deaths are counted over the 96 years. One command runs it all: `gh workflow run measure.yml --ref <branch> -f suite=instrument`.

The guarded figures are the pooled median, sum of the living, wildlife-free years, extinct years and starved years. Their bounds are computed from the best pooled figures: median minus 1.25 dwarves, sum minus 13 dwarves, wildlife-free minus 2.5 seeds, extinct years plus 2 and starved years plus 2. Each tolerance is wider than the measured spread of its pooled figure: splitting each of two commits' sixteen shifts into two sets of eight in every way (25,740 splits), the two sets' means differed by at most 1.06 in the median, 12.5 in the sum and 2.25 in wildlife-free years, and the counts by one extinct year and one starved year over twelve shifts of master before T-509's fix (`WILDLIFE_TOLERANCE`, the reference and the best figures are in `test/perf/wildlife_year_constants.ts`). A regression of the size T-481 fixed, one fortress starving to extinction, adds an extinct and a starved year in every timeline it happens in, and is blocked when it happens in three or more of the eight (taken out of T-509's second set of eight shifts, it is blocked at 8, 6, 4 and 3 of 8 and passes at 2); a loss of twelve dwarves from every sample's sum, a whole fortress, is blocked on the sum alone there (129.5 against 130); a change that costs one seed half its dwarves in every timeline is within the noise and passes. Need deaths, the worst and the second-worst seed are reported, not guarded: one fortress's year turns on which dwarf an animal reaches first, and timeline shifts move single seeds by up to thirteen living. Block a change when any bound fails, or when three or more of the five guarded figures fall together by more than half their tolerance against the latest accepted pooled row (the reference), so an earlier tolerated drop is not counted again on a later change. Keep that reference alongside the best figures used for the bounds; the verdict prints both rows to commit when the change is accepted, and they are updated in the same commit, retaining earlier better bounds when a tolerant figure falls. Always record the pooled before and after rows. A verdict over other shifts, or over samples of two commits, prints its table and fails. The survival targets remain unchanged.

The verdict's table lists each shift's row and its living by seed, so a seed that changes outcome class or moves by five or more living between shifts is seen in every run; forest seeds 1 and 2 and taiga seed 1 do so on unchanged code. The cohort stays at twelve seeds and eight shifts, which the runners play in parallel in about the time of one sample; the pooled sum of the living is the guard that unstable seeds cannot flip alone. The seed records, the worst and the second-worst outcome remain in every measurement.

### The twenty-seed sweep

`test/perf/three_years_seeds.test.ts` plays the three-year fortress for three years on twenty seeds: seven at peril 0, seven at peril 2 and six at peril 4. Each seed asserts its own invariants and witnesses and writes its figures to `THREE_YEARS_SEEDS_OUT`; the file's last test prints one sweep's set figures and asserts none of them.

**A change is judged over four sweeps, never one.** The same code shifted a few ticks before the opening plays different years: on master before T-512, ten sweeps shifted 0 to 450 ticks moved the living at year 3 between 718 and 973, the dwarf deaths between 119 and 172 and the extinct fortresses between 0 and 4; peril-0 fortresses had need deaths in four of the 70 peril-0 timelines (`three-years-p0-3` in three, 1 to 16 dead), and one sweep of the ten broke the set rule a single sweep was held to ([measurement](../../reports/audits/2026-11-06-t513-sweep-verdict.md)). So `measure.yml`'s `sweep` suite plays every seed four times in parallel, the same commit shifted 0, 50, 100 and 150 ticks before the opening (`THREE_YEARS_SHIFT`; `SWEEP_SHIFTS` in `test/perf/three_years_sweep.ts`), and its verdict job (`test/perf/three_years_sweep_verdict.test.ts`) pools them. The shifts are 50 ticks apart and no more than 400 because other shifts fall together: shifts 2 to 10 end year 3 with the same world hash on every seed measured but one, and shifts 450, 500 and 550 on most seeds, while shifts 0 to 400, 50 apart, are each a timeline of their own on every seed ([hashes](../../reports/data/2026-11-06-t513-small-shift-hashes.txt)). One command runs it all: `gh workflow run measure.yml --ref <branch> -f suite=sweep`.

Two versions of the code are compared on the same immigration rolls: a season's roll is fixed by the world seed, the year and the season (21 § Evaluation, T-652), so a wave of another size in one of them no longer reshuffles every later roll of that fortress, as it did before T-652 ([T-650](../../reports/data/2026-11-20-t650-peril-4-immigration.md)).

The pooled figures are means over the four sweeps: fortresses alive at the end of year 1 (of 20), peril-0 fortresses past embark size at the end of year 3 (of 7), peril-0 fortresses with a dwarf dead of hunger or thirst (of 7), dwarves living at the end of year 3 and dwarf deaths; extinct fortresses and need deaths are reported.

The set rule is read over the pool: on average at least 18 of the 20 fortresses are alive at the end of year 1, at least 6 of the 7 peril-0 fortresses are past embark size at the end of year 3, and at most 1 of the 7 peril-0 fortresses has a dwarf die of hunger or thirst. Survival and hunger at peril 0 are rules over the set, not over each seed, since a single seed's outcome flips under changes that do not aim at it, and over the pool, not one sweep, since one sweep's count flips too. Over the pool that is at most 8 of the 80 fortress-timelines dead at year 1, at most 4 of the 28 peril-0 timelines at or below embark size and at most 4 of the 28 with need deaths, so a peril-0 fortress that starves in every timeline spends the whole allowance. On master, every set of four of the ten shifts pooled to 19.25 to 20 alive, 7 grown and 0 to 1 with need deaths: alive and grown far inside the rule, hunger at its limit in the unluckiest set.

The living and the deaths are guarded from the best pooled figures: living at least the best minus 80, deaths at most the best plus 30 (`SWEEP_TOLERANCE`, `SWEEP_MEASURED`). Each tolerance is about two and a half times the noise of a four-shift mean against the eight-shift best figures, measured under the fixed rolls by T-662 ([measurement](../../reports/data/2026-11-22-t662-sweep-noise.md)): over eight shifts of master `f83df33f` and three four-shift sweeps of master's codes around it (16 degrees of freedom), one sweep's figures have a standard deviation of 52.3 living and 18 deaths, so a four-shift mean stands 32 living and 11 deaths (one standard deviation) from an eight-shift one; over every pair of disjoint sets of four of the eight shifts (35 pairs) the means differed by at most 75.25 living and 18 deaths. The shared rolls halved the living's noise (92.4 a sweep over T-580's eight shifts, 38.3 to 8.6 at peril 0 alone) and so its tolerance, 100 before; the deaths' noise is the timeline's raids and ambushes, which the rolls do not touch (16.8 a sweep over T-580's shifts), and its tolerance is kept. A rise of 30 deaths or a loss of 80 living is blocked half the time, one of 44 deaths or 121 living nine times in ten. Inside the bounds, the verdict names a figure worth tracing by seed before it is accepted (`SWEEP_TRACE`): living 65 or more under the best or deaths 22.5 or more over it, about twice the noise; nearer is noise, and two sweeps of nearly the same code at the same shifts differ by up to about 25 deaths (twice the 12.7 of a difference of two four-shift means), as master's 97.75 to 120.25 of 2026-11-22 did. Extinct fortresses and need deaths are reported, not guarded: which fortress a raid finds weak turns on the timeline, and pooled they still differ by up to 2.5 extinct fortresses and 8 need deaths between two sets of four. Block a change when any bound fails. The verdict prints the reference and best rows to commit when the change is accepted; they are updated in the same commit, retaining an earlier better figure when a tolerated one falls. Always record the pooled before and after rows. A verdict over other shifts, over samples of two commits or with a seed missing prints its table and fails.

What it catches, taken out of four other shifts of master (200 to 350, before T-512) judged against the bounds below ([cases](../../reports/data/2026-11-06-t513-regressions.txt)): unchanged, they pass (19.5 alive, 7 grown, 0.25 with need deaths, 852.5 living, 142 deaths). A peril-0 fortress starving out (23 dead) in four of four timelines is blocked on hunger, in two of four it passes; two starving in every timeline are blocked on hunger and deaths. Three fortresses dead before year 1 in every timeline are blocked on the alive count and deaths, in two of four they pass (18.25 alive, 173 deaths). Forty more deaths and forty fewer living in every sweep are blocked on deaths, twenty pass; eighty fewer living with no death (fewer waves) are blocked on the living, forty pass. One peril-0 fortress staying at seven in every timeline passes (6 grown), two are blocked. A rise in deaths the size T-482 seemed to bring (about fifty a sweep) is blocked; one of twenty is within the noise.

The verdict's table lists each sweep's row and each seed's year-1 and year-3 population, deaths, need deaths and extinction by shift, so a seed that flips between timelines is seen in every run. It also prints, as report lines under no rule, how the script answered the sprung ambushes and how strong a squad each fortress fielded: the strongest squad of each fortress by shift (its members armed in metal, their body armour's metal and their best weapon skill, looked at once a day), how many fortress-timelines cleared each ambush bar, and by peril how many cleared each and on which days they first did, every sprung ambush by the script's first answer to it (fought, stood down, met at the gate, in the halls, or with another threat), and the ambushes that ended by that answer with the dwarves dead from their spring until the party was gone (those of the squad among them) and the members of the ambush felled. The journal's ambush census notes the same answer and the squad as each ambush found it. The best figures are the means of eight shifts (0 to 350) of the same code, 1126.63 living and 102.5 deaths, so the bounds are 18, 6, 1, 1046.63 and 132.5 ([T-662](../../reports/data/2026-11-22-t662-sweep-noise.md)). The reference before it, `2e36fb6d` (T-580, on master `0c2e88b7`), was 19.5 / 7 / 0 / 1010.5 / 137 with best figures 987.75 and 131.88 and bounds 887.75 and 161.88, measured when each shift drew its own rolls; master had since moved 139 living and 29 deaths past its best figures, so those bounds let a loss of over 200 living or a rise of nearly 60 deaths through. A best figure is a mean of eight shifts and not one lucky set of four: the minimum of many noisy pooled figures sits below the code's true level, and a bound set from it blocks unchanged code. The noise was measured on an earlier master, whose same shifts pooled to 20, 7, 0.75, 903.75 and 141.75; on master `6e6a6ec3` single sweeps ranged from 124 to 184 deaths. The cost is 80 jobs of 2 to 18 minutes, about 167 job-minutes a sweep. GitHub's free runners take twenty jobs at a time for the whole repository, so a verdict takes about 40 minutes when nothing else is queued (37 and 39 minutes measured), and waits behind other runs: twelve sweeps (240 jobs) took 2 hours 40 minutes behind another task's runs. Eight sweeps would narrow the tolerances by about a third and take about 80 minutes; four is the compromise.

CI runs only on demand. `.github/workflows/ci.yml` runs `lint`, `typecheck`, `content:check`, `strings:check`, `interface:check`, `docs:check`, `test`, `build` and `test:e2e`. `.github/workflows/measure.yml` runs one heavy measurement, such as the twenty-seed sweep with one job per seed and shift and its verdict. How to start one and read its results: [tooling.md § Running tests on GitHub](../04-implementation/tooling.md#running-tests-on-github).

## The docs link check

`scripts/docs-links-check.mjs` reads every Markdown file under `docs/`, `reports/` and `agents/`, and the root `README.md`. It fails on an inline link or image whose relative target does not exist. It skips URLs, in-page anchors, fenced code and inline code, and it does not resolve the heading after a `#`. A task that moves or renames a document fixes every link to it in the same commit; the check is how it finds them. `test/unit/docs-links-check.test.ts` runs the same check, so `npm test` fails on a broken link too.

## Test naming

`describe('T-123 designations', ...)` for unit tests, with the id of the task that adds them; scenario ids as file names (`tr_dig_room.scenario.ts`). A test that pins a choice made under the [ambiguity protocol](ambiguity-protocol.md) says in its name what it pins; one that pins a decision-log row or a contradiction names the row: `it('D-007: ...')`, `it.todo('C-nnn: ...')`. Existing tests keep the labels they were written with (`T-M1-03`, `F-12`, `U-03`).
